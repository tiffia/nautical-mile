What this directory is for

The `k8s/` directory contains Kubernetes manifest files. These are instructions for Kubernetes to:
- create a running app instance
- expose it on a network port
- keep it running as a deployment

This repo is a small Python app, and the Kubernetes files are the deployment blueprint for it.

1) `k8s/deployment.yaml`

This file tells Kubernetes:
- create a Deployment
- run 1 replica of the app
- use a Docker image
- expose port 5000
- set resource limits

The file is:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: learning-tracker
  labels:
    app: learning-tracker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: learning-tracker
  template:
    metadata:
      labels:
        app: learning-tracker
    spec:
      containers:
        - name: tracker
          image: tiffiajose/learning-tracker:v1
          ports:
          - containerPort: 5000
          resources:
            limits:
              memory: "128Mi"
              cpu: "200m"
```

Field-by-field:

- apiVersion: apps/v1
  - says “use the Deployment API from Kubernetes v1”
  - this is the Kubernetes resource version

- kind: Deployment
  - means this object manages a set of Pods
  - it keeps the app running and restarts it if it crashes

- metadata:
  - describes the object itself
  - name: learning-tracker
    - the name of the deployment
  - labels:
    - app: learning-tracker
    - this is a label used to identify this app

- spec:
  - desired state configuration

- replicas: 1
  - run one instance of the app
  - if this were 3, K8s would keep 3 pods running

- selector:
  - tells the Deployment which Pods belong to it
  - matchLabels.app: learning-tracker
    - only matches Pods labeled app=learning-tracker

- template:
  - this is the blueprint for the Pods the Deployment creates

- metadata.labels.app: learning-tracker
  - the Pod gets this label so the Deployment can manage it and the Service can find it

- spec.containers:
  - list of containers in the Pod

- name: tracker
  - container name

- image: tiffiajose/learning-tracker:v1
  - the Docker image to run
  - this image should already exist in Docker Hub or your registry

- ports:
  - containerPort: 5000
  - the app inside the container listens on port 5000

- resources:
  - limits:
    - memory: "128Mi"
    - cpu: "200m"
  - max allowed resources for this container
  - means:
    - use no more than 128 MB RAM
    - use no more than 200 millicores of CPU

So, in plain English:
“This tells Kubernetes to run one copy of the app using the Docker image, expose port 5000, and cap the resource use.”

2) `k8s/service.yaml`

This file creates a Service, which gives the app a stable network endpoint.

The file is:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: learning-tracker-service
spec:
  type: NodePort
  selector:
    app: learning-tracker
  ports:
    - port: 5000
      targetPort: 5000
      nodePort: 30080
```

Field-by-field:

- apiVersion: v1
  - this is the core Kubernetes API version for Services

- kind: Service
  - means this object is a network service
  - it exposes Pods to other resources

- metadata.name: learning-tracker-service
  - name of the Service

- spec:
  - service settings

- type: NodePort
  - exposes the app on a port on the cluster node
  - this is a simple way to access the app from outside the cluster

- selector:
  - app: learning-tracker
  - selects Pods with label app=learning-tracker

- ports:
  - port: 5000
    - the port the Service listens on internally
  - targetPort: 5000
    - forwards traffic to the Pod’s port 5000
  - nodePort: 30080
    - the externally reachable port on the node
    - in a real cluster, you’d usually access it on http://<node-ip>:30080

So, in plain English:
“This Service points to the app Pods and exposes them on port 30080, forwarding traffic to the app’s port 5000.”

3) How the app is deployed in Kubernetes step by step

Here’s the flow:

1. You build a Docker image
   - usually from `Dockerfile`

2. You push that image to a registry
   - here it is tiffiajose/learning-tracker:v1

3. Kubernetes reads `k8s/deployment.yaml`
   - it sees “run 1 pod with this image”

4. The Deployment creates a Pod
   - the Pod has label app=learning-tracker

5. Kubernetes reads `k8s/service.yaml`
   - it sees “route traffic to Pods with label app=learning-tracker”

6. The Service forwards traffic to the Pod
   - incoming traffic on port 30080 goes to port 5000 inside the container

7. The app is reachable from outside the cluster
   - typically via http://<node-ip>:30080

So the connection is:

- Deployment creates Pod
- Service selects Pod
- NodePort exposes it externally

4) How Argo CD fits into this project

There is also `argocd-app.yaml`. In this repo, it is currently empty.

That matters because:
- Argo CD is a GitOps deployment tool
- it watches Git repositories for changes
- when manifests in Git change, it automatically applies them to the cluster

Typical Argo CD flow:

- you commit YAML files to Git
- Argo CD detects the change
- it compares desired state in Git with actual state in Kubernetes
- it syncs the cluster to match the repo

So instead of manually running:
- kubectl apply -f k8s/deployment.yaml
- kubectl apply -f k8s/service.yaml

you could let Argo CD do it automatically.

In other words:

- Git is the source of truth
- Argo CD is the automation engine
- Kubernetes is the runtime environment

If `argocd-app.yaml` were properly written, it would describe an Argo CD Application that points to this repo and the path to the Kubernetes manifests.

Example conceptually:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: learning-tracker
spec:
  project: default
  source:
    repoURL: https://github.com/tiffia/nautical-mile
    targetRevision: HEAD
    path: k8s
  destination:
    server: https://kubernetes.default.svc
    namespace: default
```

This would tell Argo CD:
- watch this repo
- look in the k8s folder
- deploy those YAMLs to the cluster

Important note:
- in your current repo, `argocd-app.yaml` is empty, so Argo CD has no application definition yet

5) Quick summary

- `k8s/deployment.yaml` = create and run the app
- `k8s/service.yaml` = expose the app outside the cluster
- `argocd-app.yaml` = future GitOps definition for automatic deployment

## Commands
`kubectl create namespace argocd`
Creates a Kubernetes namespace named argocd—a logical space to keep Argo CD’s resources grouped. Your output confirms it was created.

`kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`
Downloads Argo CD’s installation YAML from the Argo Project’s GitHub repository and asks Kubernetes to create or update the resources described in it. The -n argocd option sets the namespace for namespaced resources. Some resources in the manifest, such as cluster-wide permissions or custom resource definitions, apply to the whole cluster.

This installs Argo CD in the cluster; it doesn’t necessarily make its web interface publicly accessible. Also, the stable URL can change as new releases are published, so for a production setup you’d typically use a version-specific manifest.
